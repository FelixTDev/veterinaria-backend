# Especificación: Vacunas y Vacunas Aplicadas

## Alcance

Implementar el catálogo de vacunas y el registro inmutable de vacunas aplicadas dentro de una atención médica existente, sin modificar el esquema PostgreSQL, las entidades existentes ni `pom.xml`.

## API

### Catálogo

- `POST /api/v1/vacunas` — crear; `ADMINISTRADOR`.
- `GET /api/v1/vacunas` — listar; `ADMINISTRADOR` o `VETERINARIO`.
- `GET /api/v1/vacunas/{id}` — detalle; `ADMINISTRADOR` o `VETERINARIO`.
- `PUT /api/v1/vacunas/{id}` — actualizar nombre y descripción; `ADMINISTRADOR`.
- `PATCH /api/v1/vacunas/{id}/estado` — activar/desactivar; `ADMINISTRADOR`.

No se implementa `DELETE`.

### Aplicaciones clínicas

- `POST /api/v1/atenciones-medicas/{atencionId}/vacunas` — crear una aplicación.
- `GET /api/v1/atenciones-medicas/{atencionId}/vacunas` — aplicaciones de una atención.
- `GET /api/v1/mascotas/{mascotaId}/vacunas-aplicadas` — historial paginado.

Las lecturas clínicas requieren `ADMINISTRADOR` o `VETERINARIO`.

## Reglas de negocio

- El nombre se recorta, es obligatorio y se valida con `existsByNombreIgnoreCase`.
- La restricción PostgreSQL actual es case-sensitive; se captura también `DataIntegrityViolationException` para duplicados exactos. La carrera `Rabia`/`RABIA` permanece documentada y no se corrige modificando el esquema.
- Una vacuna inactiva no puede aplicarse, pero aparece en históricos.
- `fechaAplicacion` se deriva exclusivamente de `AtencionMedica.fechaAtencion.toLocalDate()`.
- `proximaFecha` es opcional; si se informa, debe ser `>= fechaAplicacion`. No se calcula automáticamente.
- `lote` es opcional, se recorta y tiene máximo 80 caracteres; vacío recortado se convierte en `null`.
- `observaciones` es opcional, se recorta y tiene máximo 300 caracteres; vacío recortado se convierte en `null`.
- No se impide repetir la misma vacuna en una atención, porque el esquema no define esa unicidad.
- La aplicación requiere atención existente, cita `MEDICA`, cita `ATENDIDA`, vacuna activa, usuario activo con rol veterinario y coincidencia exacta entre el `uid` JWT y el veterinario responsable.
- Una aplicación no se edita ni elimina mediante API.
- Registrar una aplicación no modifica datos clínicos ni el estado de la cita.

## Persistencia y rendimiento

El historial se pagina y filtra en PostgreSQL, ordenado por `fechaAplicacion DESC, id DESC`. Las consultas cargarán relaciones to-one necesarias mediante `EntityGraph`, JPQL o proyección, sin consultas dentro de loops ni fetch join de colecciones paginadas. No se agrega locking pesimista.

## DTOs

Catálogo: `CrearVacunaRequest`, `ActualizarVacunaRequest`, `CambiarEstadoVacunaRequest`, `VacunaResponse`, `VacunaResumenResponse`.

Aplicaciones: `AplicarVacunaRequest`, `VacunaAplicadaResponse`, `VacunaAplicadaResumenResponse`.

`AplicarVacunaRequest` no contiene identificadores de atención, mascota, cita, veterinario ni `fechaAplicacion`.
